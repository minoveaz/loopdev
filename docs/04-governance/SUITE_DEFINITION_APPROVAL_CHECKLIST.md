# Suite Definition Approval Checklist

Complete this checklist before implementation code or a suite-specific execution
track is created. Link evidence beside each item in the owning track.

## Intent and boundaries

- [ ] Problem, target users, value, and success signal are explicit.
- [ ] Included responsibilities are listed.
- [ ] Excluded responsibilities are listed.
- [ ] Adjacent suites and ownership boundaries are identified.

## Module map

- [ ] Initial modules are named and prioritized.
- [ ] Future modules are separated from committed scope.
- [ ] Module dependencies and sequencing are recorded.
- [ ] Shared capabilities have an explicit owner.

## Experience

- [ ] Suite entry point is defined.
- [ ] Navigation and global context are defined.
- [ ] Primary workspace for each initial module is identified.
- [ ] Empty, loading, error, and insufficient-permission states are covered.
- [ ] Cross-module transitions are described.

## Contracts and security

- [ ] Canonical entities and ownership are documented.
- [ ] Tenant boundary and isolation strategy are documented.
- [ ] Roles, permissions, and administrative actions are documented.
- [ ] Events and integrations have owners and contracts.
- [ ] Audit, retention, and sensitive-data concerns are recorded.

## Components and impact

- [ ] Existing components and patterns were audited.
- [ ] New design-system components are justified.
- [ ] Duplicate implementation risk is recorded.
- [ ] Package, registry, migration, and operational impact is assessed.
- [ ] Validation strategy and required checks are identified.

## Module readiness

- [ ] Each initial module has a UX specification.
- [ ] Each initial module has a component audit.
- [ ] Each initial module has a domain contract.
- [ ] Each initial module has an impact assessment.
- [ ] Each initial module has an implementation handoff.

## Governance and handoff

- [ ] CRM dry-run or another precedent review is complete.
- [ ] Open decisions are recorded with an approver.
- [ ] Risks, blockers, dependencies, and deferred scope are explicit.
- [ ] Phase acceptance criteria and evidence are defined.
- [ ] The next concrete action is named.
- [ ] User approval is recorded before implementation starts.
