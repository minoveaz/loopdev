# CRM component catalog

This is the normalized Phase 1 catalog for the 27 Markdown sources in
`origin/docs/2026-execution-roadmap:docs/06-product/crm/`. It is an inventory
and contract decision aid, not authorization to implement UI. A row is a
proposed component when its name appears in an audit, UX composition,
contract, or implementation handoff. Names in parentheses are source aliases
normalized to the same implementation boundary.

## Estado de integración

This catalog was reconciled against `origin/develop` on 2026-09-04. The
historical CRM foundation work is present in `develop` through squash or
equivalent delivery commits, including contacts, leads, Customer 360, tasks,
pipeline, G0 controls and the shared UI foundation. The catalog remains the
consolidated design inventory; implementation status and delivery evidence
must be read from the current contracts, routes, migrations and tests.

The active delivery branches at the time of review are:

- `feature/leads-frontend-implementation`: lead list, capture, detail,
  conversion routes and certification coverage.
- `feature/communications-core-implementation`: Communications Core,
  WhatsApp authorization, dispatch and worker foundations.
- `feature/crm-communications-inbox-implementation`: CRM inbox UI, inbox
  actions, templates and communication state handling.

The historical branches reviewed during this reconciliation are retired and
are not additional implementation sources. No CRM code should be recovered
from those branch names without first checking `origin/develop` and the active
delivery branches.

**Decision vocabulary:** `reuse` means use an existing contract as-is;
`variant` means a CRM-owned presentation over an existing primitive;
`compose` means combine existing primitives and CRM data; `create` means a new
CRM-owned contract. No CRM proposal is eligible for promotion to
`@loopdev/ui` without an agnostic contract, a second real consumer, tests,
registry evidence, and explicit approval.

## Required contract applied to every row

| Field | Normalized requirement |
| --- | --- |
| Scope | Every query and mutation resolves user, organization/tenant, workspace, membership and permission server-side. Browser code never uses `service_role`; RLS denies cross-organization reads, writes and references. |
| Query states | `loading` (skeleton or progress), `empty` (safe next action), `error` (safe message, retry and trace/request id), `forbidden` (no data leakage), `success`; list consumers use cursor pagination and preserve filters. Detail consumers also support `stale` and `conflict` where the source contract requires them. |
| Mutation states | `idle`, `pending`, `success`, `validation-error`, `forbidden`, `conflict`, and `server-error`; critical commands use idempotency keys, expected version, audit events and no unsafe optimistic display. |
| Accessibility | Semantic landmarks and headings, labelled inputs, keyboard focus order, visible focus, `aria-live` for async result, table/list semantics, and an accessible menu/action alternative for drag-and-drop. Never encode state by colour alone. |
| Consumer meaning | “Real consumer” is a concrete approved route, Canvas mode, or UAT journey. Repository implementation evidence is listed separately; a legacy prototype is not treated as an authoritative consumer. |

## Cross-cutting duplicate and ownership decisions

1. `SuiteRuntime`, `SuiteCanvas`, headers, controls, feedback states, tables,
   pagination and dialogs are shared infrastructure; none receives CRM rules.
2. Contact/Lead/Opportunity/Task tables and record views are separate CRM
   contracts even when they compose the same primitives. A generic table or
   card is not a license to share entity semantics.
3. `ContactDetailPanel`, `LeadRecordPreview`, `Customer360Preview` and
   `OpportunityRecordView` are not one universal “record panel”: they have
   different read models and mutation permissions. They may share layout
   primitives only.
4. `ActivityItem`, `TimelineEvent`, `ActivityTimeline` and `Customer360Timeline`
   converge on the shared append-only activity contract; deduplication is
   `sourceType + ':' + sourceId`, never title/date.
5. `CreateOpportunityFromLead` has one feature contract consumed by Leads and
   Pipeline. It must not be implemented twice.
6. Existing legacy CRM code is implementation evidence, not authority. In
   particular, the current Lead Kanban uses legacy Lead stages and local state,
   while the roadmap contract requires authorized cursor queries, stable
   statuses, idempotency and audit.

## Evidence gaps and implementation gates

- Reconcile roadmap CRM contracts with current `packages/contracts/src/crm`
  schemas before generating types or migrations.
- Define the canonical route/API read models for the documented routes; the
  current app contains legacy `/sales-crm` pages and API endpoints but not all
  approved route compositions.
- Add registry entries only after a component has a real second consumer;
  current registry evidence covers shared primitives, not CRM proposals.
- Approve exact role/capability matrices, field visibility/redaction,
  stage/status transitions, filter/sort schemas, pagination limits and
  idempotency transaction boundaries.
- Add contract, RLS, accessibility, route and state tests before any `create`
  row is implemented. This catalog intentionally adds no UI components.
